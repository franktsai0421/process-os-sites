> [!IMPORTANT]
> **2026-09-26 最新規格修訂（正式取代舊的理由、Excel、操作歷程 UI 及檢查週期規格）**：
> 1. **標準啟用與檢查規則分開**：拆分為獨立的「標準狀態」（checkbox「啟用此標準」）與「檢查規則」卡片。啟用控制是否使用該標準並計入產品覆蓋；停用保留內容與規則但不計入有效覆蓋；兩者互不連動。
> 2. **檢查規則採 IQC 方式，每項限一組**：移除月/季/年/自訂多選 checkbox，改為單一檢查規則卡片。方式單選「未設定／按批次／按時間」。按批次包含 AQL、固定件數（正整數件）、批次數量基準、自訂取樣說明；按時間包含每週、每月、每季、每半年、每年、自訂（不可空白）。每項目最多只能有一組有效規則，列表改用「檢查規則」摘要與「標準狀態」兩欄呈現。
> 3. **舊週期資料相容**：舊單一時間週期自動對應「按時間」相應頻率；全未勾選對應「未設定」；多週期保留原值標示「待確認單一檢查規則」，列入問題與待補由使用者選定一組後保存。
> 4. **全面取消 FQC 理由輸入**：新增/修改/刪除錯誤代碼與檢查項目、產品關聯、送審、解除送審、主管發回修改全部不再要求輸入理由，移除輸入框與驗證。備註保留且可空白，歷史理由完整保留不刪除。
> 5. **完整草稿與審核流程**：待審內容鎖定；支援解除送審與主管發回修改，成功後恢復同一原草稿可編輯，保留所有內容、圖片、關聯與歷史。
> 6. **移除 FQC Excel 匯入／匯出**：移除匯入、匯出及範本下載按鈕與事件，保留所有已匯入資料、圖片、草稿及歷史版本。
> 7. **操作歷程改為「問題與待補」**：原位置改為問題與待補卡片，無問題精簡顯示「目前無待處理問題」，有問題展開列出受影響資料、原因、建議與「前往修正」直達按鈕。

## 二、資料關係及編碼規範 (REQ-FQC-02)

- **[REQ-FQC-02-01] 層級關聯**：嚴格遵循 `A／B／C 線 → 產品類別 → 錯誤代碼 → 檢查項目 → 適用產品` 之關聯層級。
- **[REQ-FQC-02-02] 關聯既有主資料**：直接關聯既有產品類別與產品主資料，不得建立重複的產品主資料記錄。
- **[REQ-FQC-02-03] 完整產品資訊**：UI 及資料流中顯示產品完整編號（Code）、產品名稱（Name）、規格（Specification）。
- **[REQ-FQC-02-04] 獨立錯誤代碼列表**：錯誤代碼具備獨立管理列表，支援新增、選取、修改、刪除。選取錯誤代碼後，下方僅顯示其所屬之檢查項目，避免在檢查項目表中反覆出現父層代碼名稱等大量重複資訊。
- **[REQ-FQC-02-05] 編碼規格與自動接續**：
  - 類別範例：`BORUAXE1021`
  - 錯誤代碼範例：`BORUAXE1021-FQC-L01`（格式為 `<類別代碼前綴>-FQC-L<2位數>`）
  - 錯誤名稱範例：`Ngoại quan`
  - 檢查編號範例：`BORUAXE1021-FQC-L1-01`（格式為 `<類別代碼前綴>-FQC-L<L號>-<2位序號>`）
  - **歷史前綴相容**：5 個特殊類別（`BRX1021-CO3360`、`DAUTUOICAY-RUAXE`、`ONGHOI-CAOAP/BRX-CAOAP`、`PHAODIEN`、`PVC(2)`）在 Excel 中前綴無符號或有拼寫特徵，必須**保留來源合法編碼**；新增時自動偵測該類別既有前綴並接續各自最大序號，編號在 UI 上為唯讀。
  - **唯一性與併發**：後端確保編號全域唯一，妥善處理多使用者同時新增之序號衝突；刪除之編號不重用；修改名稱絕不變更編號。
- **[REQ-FQC-02-06] 級聯防護**：若錯誤代碼下仍包含檢查項目，禁止直接刪除該錯誤代碼，系統必須提示「請先刪除或移轉所屬子項目」。
- **[REQ-FQC-02-07] 停用與刪除隔離**：停用（`isEnabled = false`）與物理/邏輯刪除嚴格分開，保留歷史版本、檢驗紀錄及其圖片引用。

## 三、後台 UI 規格 (REQ-FQC-03)

- **[REQ-FQC-03-01] 入口與導覽**：入口維持「資料後台 → 品質系統 → FQC」分頁，保持既有側邊欄與頂部分頁導覽結構。
- **[REQ-FQC-03-02] 垂直區塊佈局**：
  1. **版本／草稿區**：
     - 顯示目前查閱版本（例如 `FQC - V3`）、版本狀態 badge（已核准 / 草稿 / 主管審核中）、當前生效版本。
     - 顯示選擇版本/草稿下拉選單（標記版本號、狀態、修改者、更新時間）。
     - 操作按鈕：查閱已生效版時顯示「開始修改／刪除資料」；草稿中顯示「儲存草稿」、「送出主管審核」；提供「前往版本確認平台」按鈕。
  2. **版本紀錄與操作歷程**：預設收合的 `<details>` 區塊，標題包含歷程筆數，展開後按時間倒序顯示歷程清單。
  3. **篩選列**：
     - 線別下拉選單（全部線別 / A / B / C）。
     - 產品類別下拉選單（依選定線別聯動過濾）。
     - 搜尋產品輸入框（即時過濾產品編號或名稱）。
     - 按鈕：「匯入 Excel」、「匯出全部 Excel」。
  4. **錯誤代碼列表**：表格顯示錯誤代碼、名稱、所屬檢查項目數。右上角提供「＋ 新增錯誤代碼」按鈕。點擊資料列即高亮並切換下方檢查項目。
  5. **選定代碼的檢查項目**：標題顯示選中之錯誤代碼與名稱。右上角提供「＋ 新增檢查項目」（自動帶入當前錯誤代碼）。表格顯示檢查編號、項目名稱、工具、月/季檢查標記、包含產品摘要（如「▶ 2 個產品」）、啟用狀態。
  6. **產品適用覆蓋矩陣**：可展開/收合區塊，標題標註未涵蓋產品數量（如「▼ 產品適用矩陣 · 1 個產品尚無啟用標準」）。
  7. **未涵蓋產品列表**：緊接在矩陣下方，精簡表格列出未涵蓋產品，避免無效大面積空白。
- **[REQ-FQC-03-03] 權限與彈窗規範**：一般瀏覽狀態下所有控制項唯讀；進入草稿編輯模式後，依角色權限顯示新增、修改、刪除按鈕。新增與修改一律使用彈出視窗（Modal）。
- **[REQ-FQC-03-04] 視覺簡潔**：主頁面上**不要**顯示獨立的「本草稿變更理由與明細」大型獨立區塊。

- **[REQ-FQC-04-01] 錯誤代碼編輯表單 (Modal)**：
  - 垂直單欄堆疊排版（「標籤在上、輸入框在下」）：產品類別、錯誤代碼（自動接續）、錯誤名稱、變更理由。
  - 標籤與輸入框間距 6–8px，欄位間距約 16px，輸入框與 textarea 填滿表單寬度。

  - 檢查項目名稱（文字輸入框，例如 `Nhãn ( 標籤尺寸、文字、外觀 )`）。

  - 系統資訊提示：顯示目前版本、修改帳號、儲存時間。
  - 底部操作：`儲存至草稿`（主按鈕）、`取消`（次按鈕）。

## 五、覆蓋矩陣規格 (REQ-FQC-05)

- **[REQ-FQC-05-01] 矩陣結構**：列（Rows）為 FQC 檢查編號與項目名稱；欄（Columns）為所屬類別之產品。產品標題欄可適度縮寫，但必須提供 Tooltip 或展開查看完整產品編號、名稱、規格。
- **[REQ-FQC-05-02] 狀態符號與標記**：
  - `✓`：表示該產品已納入此檢驗項目且項目為啟用狀態。
  - `—`：表示未納入。
  - 已納入但該檢查項目處於停用狀態（`isEnabled = false`）時，採用獨立視覺標記（如淡灰標記或刪除線符號），不計入有效覆蓋。
- **[REQ-FQC-05-03] 矩陣互動 - 點擊 ✓**：草稿中直接取消該產品關聯並以現有修訂檢查儲存；不開修改彈窗，項目啟用狀態與其他欄位不變。
- **[REQ-FQC-05-04] 矩陣互動 - 點擊 —**：直接加入該產品並儲存，不新增編號；修改頁讀取同一關聯。儲存中鎖定矩陣；失敗顯示錯誤並保留待重試內容，不覆蓋修訂衝突。待審／歷史版不可切換。
- **[REQ-FQC-05-05] 未涵蓋產品即時計算**：矩陣下方列出該類別中「所有啟用檢驗項目均未涵蓋」之產品清單，顯示數量提示（例如「1 個產品尚無啟用標準」）、完整產品編號、名稱、規格。**計算範圍為整個類別，絕不因上方搜尋框關鍵字、篩選條件或當前選定之錯誤代碼而發生統計誤算**。
- **[REQ-FQC-05-06] 未涵蓋產品之加入操作**：未涵蓋產品操作列提供快速加入方式：
  1. **加入既有項目（2026-09-22 簡化為批次複選視窗）**：
     - 點擊後開啟單一複選視窗，上方顯示目前產品的編號、名稱、規格與身分。
     - 跨錯誤代碼列出該類別目前草稿中的所有既有檢查項目（包含啟用與停用狀態）。
     - 每列提供 Checkbox、完整檢查編號、檢查名稱（自然換行）、啟用狀態 Badge。
     - 支援同時勾選多項、提供「全選 / 取消全選」與即時「已選取 N / Total 項」計數。
     - 底部為「確認加入並儲存草稿」與「取消」，不再開啟單一檢查項目編輯表單，不要求變更理由。
     - 確認後將該產品批次加入所有勾選項目的適用產品清單，非重複加入，未勾選項目不刪除原有產品，不新增檢查編號；停用項目不自動啟用，亦不計入有效覆蓋。
     - 儲存失敗在彈窗底端就地提示，保留勾選供重試；取消不保存。
  2. 新增檢查項目加入（彈出新增檢查項目視窗，自動預帶該產品）。
- **[REQ-FQC-05-07] 主資料聯動**：當系統主資料新增產品時，該產品自動出現在對應類別的選擇清單與覆蓋矩陣中，未經人工指派前自動列入未涵蓋產品，不自動臆測分配檢驗標準。
- **[REQ-FQC-05-08] 生效版本隔離**：草稿狀態下的矩陣變更僅在草稿內反映；正式使用端（如產線播放台、品質檢驗端）僅讀取已核准生效版本之矩陣資料。

## 六、變更理由管理 (REQ-FQC-06)（2026-09-22 更新規則，取代舊版規範）

- **[REQ-FQC-06-01] 錯誤代碼理由重用與實質變更觸發**：
  - 錯誤代碼保留變更理由欄位與重用機制。
  - 僅在新增錯誤代碼，或修改時名稱發生實質變更（`name !== existing.name`）時才要求輸入變更理由；若未修改名稱則不需填寫理由。
  - 同一草稿內已儲存過該代碼理由時，重新開啟編輯視窗自動帶回，使用者可直接沿用或補充，不清空或強迫重新輸入。
- **[REQ-FQC-06-02] 檢查項目全面移除理由要求**：
  - 新增與修改檢查項目視窗中，全面移除變更理由標籤、輸入框與必填提示。
  - 範圍涵蓋：清單編輯、覆蓋矩陣點擊（`✓` / `—`）、包含產品勾選增減、「加入既有檢查項目」單筆/批次加入、修改照片、工具、週期等所有檢查項目相關操作。
  - 原備註欄位（`note`）保留，供使用者自由輸入，可空白，不作為必填阻擋條件。
- **[REQ-FQC-06-03] 歷史理由保留與刪除防護**：
  - 歷史已存在的檢查項目理由仍保留於資料模型中，不主動以空字串覆蓋。
  - 刪除錯誤代碼或檢查項目時，彈出確認視窗仍必須收集刪除理由，並與刪除紀錄共同持久化保存。審核平台審查註記維持原規則。
- **[REQ-FQC-06-04] 就地錯誤提示與遮罩防護**：
  - 彈窗內部驗證失敗時（如錯誤代碼名稱變更未填寫理由），錯誤訊息直接在該欄位下方以紅字顯示，並為輸入框加上紅框，彈窗保持開啟不關閉。
  - 全域 `#toast` 的 `z-index` 設定為高於彈窗遮罩（`100005`），防止操作提示訊息被暗色半透明遮罩（`100000`）蓋住。

## 七、Excel 匯入/匯出與多語言 (REQ-FQC-07)

- **[REQ-FQC-07-01] 結構解析與合併儲存格**：依據欄位名稱與實體結構嚴格對齊，正確解開 `產品資料` 垂直合併之類別、錯誤代碼、錯誤名稱儲存格，並將其正確展開繼承至各列檢查項目。
- **[REQ-FQC-07-02] 原文完整保留**：使用者資料內容（包含越文聲調符號、特殊文字、空格）100% 原文保留；**不翻譯、不擅自加上中文字詞或註解**。系統介面按鈕、標題與提示訊息則遵循現有繁中/越文雙語切換機制。
- **[REQ-FQC-07-03] 匯入預覽確認**：Excel 匯入時提供預覽視窗，分類列出新增筆數、更新筆數、未變更筆數、格式錯誤筆數與將被清空之內容；經使用者明確二次確認後，始寫入當前草稿，不直接寫入生效版本。
- **[REQ-FQC-07-04] 異常回報不靜默**：若發生類別/產品無法對應、重複檢查編號或資料衝突，必須具體列出來源列號與原因，禁止隨意猜測或靜默略過。
- **[REQ-FQC-07-05] 冪等與非破壞性**：重複匯入相同檔案不應產生重複資料；來源檔案少某一筆資料不代表刪除線上既有資料。
- **[REQ-FQC-07-06] 欄位缺失與空白區分**：嚴格區分未提供欄位（如月檢查）、普通空白字串與明確清空指令（尤其是圖片、關聯產品、備註）。
- **[REQ-FQC-07-07] 圖片支援透明度**：支援真實圖片檔案及圖片關聯；若有不支援的圖片格式或形式，需明確在錯誤清單中列出，不可虛報支援。
- **[REQ-FQC-07-08] 完整匯出**：匯出功能匯出當前查閱版本之完整資料，不受前端搜尋/篩選條件限制，內容包含：
  - 無子項目的錯誤代碼
  - 已停用項目
  - 所有欄位（完整產品編號、名稱、規格、工具、頻率、關聯）
  - 真實圖片資料或持久化可存取之圖片內容（禁止匯出臨時短期失效之 URL）
  - 版本號、狀態、變更理由、備註、修改帳號、更新時間
  - 覆蓋矩陣、未涵蓋產品清單與操作紀錄可輸出為獨立工作表。
- **[REQ-FQC-07-09] 匯出重匯驗證**：匯出之檔案必須能夠再次完整匯入回系統草稿，並精確還原各項檢查項目與圖片關聯，統計數字完全一致。
- **[REQ-FQC-07-10] 審核歷史真實性**：來源檔案中附帶之歷史文字可作為備忘欄位保存，但匯入時之建立者、時間與狀態由系統實際登入身分與環境決定，絕不偽造線上核准人或審核狀態。

## 八、版本控制與審核工作流 (REQ-FQC-08)

- **[REQ-FQC-08-01] 狀態生命週期**：`草稿 (draft)` → `儲存 (save)` → `送審鎖定 (pending)` → `核准生效 (approved)`；或審核主管 `發回並填寫理由 (reject/revise)` → `草稿解鎖並保留原修改繼續編輯` → `再次送審`。
- **[REQ-FQC-08-02] 內部修訂號**：同一個草稿版本多次點擊儲存，不增加正式對外版本號（如維持 `V4` 草稿），內部使用樂觀鎖定修訂號（Revision）偵測多人併發衝突。
- **[REQ-FQC-08-03] 基準版本鎖定**：草稿必須記錄其建立時之基準版本 ID。若在此草稿送審前線上已有更新的核准版本生效，系統必須阻擋並提示衝突，舊草稿不得直接覆蓋較新的正式版本。
- **[REQ-FQC-08-04] 審核平台版面**：保留既有「版本確認平台」左側案件清單、右側詳細差異比較之經典版面。
- **[REQ-FQC-08-05] 增加品質分頁**：在版本確認平台頂部既有「主資料送審」、「製程版本確認」旁，**新增「品質系統資料庫」分頁**，並在分頁標籤上顯示待確認案件總數。
- **[REQ-FQC-08-06] 四庫案件並存**：在「品質系統資料庫」分頁內，可分別查閱 FQC、IQC、IPQC、例行報告資料庫各自之案件、版本號、狀態、修改者、送審者與送審時間。
- **[REQ-FQC-08-07] 完整差異比對**：右側比對視窗完整呈現：錯誤代碼增刪改、檢查項目增刪改、產品加入/移除、圖片新增/更換、啟用開關、月/季檢查頻率變動、各項變更理由。
- **[REQ-FQC-08-08] 權限連動**：依據使用者角色權限（`approval.approve`、`approval.withdraw` 等）提供核准或發回按鈕；資料後台入口狀態與審核平台狀態即時雙向連動。
- **[REQ-FQC-08-09] 送審快照不可變性**：點擊送出主管審核前，必須完成所有資料與圖片之持久化儲存，形成不可在背景被悄悄竄改的凍結快照（Pending Snapshot）。
- **[REQ-FQC-08-10] 發回與核准歷史**：發回時保留所有已修改內容與發回審核歷程；核准時自動將原生效版本切換為歷史版本（`superseded`），將本版切換為當前生效版本（`approved`），並完整保留歷程。
- **[REQ-FQC-08-11] 稽核身分真實性**：建立者、修改者、送審者、審核者帳號分開獨立記錄，由後端登入身分決定；歷史缺漏顯示未記錄，不虛構身分。
- **[REQ-FQC-08-12] 冪等操作防護**：核准與狀態切換操作具備冪等性，網路重試或使用者快速重複點擊不產生重複案件或狀態錯亂。

## 九、草稿遺失修復機制 (REQ-FQC-09)

- **[REQ-FQC-09-01] 流程查明與不重做有效修復**：深入查明共用之保存與載入流程（涵蓋製程編輯台與品質資料庫）；檢視既有分支中之有效修復（如 `fix/process-editor-draft-persistence` 與 `test-editor-draft-persistence.cjs`），保留有效邏輯，不盲目重做或覆蓋。
- **[REQ-FQC-09-02] 後端持久化存儲**：草稿資料必須持久保存在後端（Cloudflare D1 / R2），絕不能僅保存在記憶體、`localStorage` 或 `sessionStorage` 中。**使用者登出絕對不能刪除後端已保存之草稿**。
- **[REQ-FQC-09-03] 全量資料保存**：儲存草稿時，必須完整保存所有新增/修改/刪除之錯誤代碼、檢查項目、產品勾選清單、圖片關聯、變更理由、備註、啟用設定、版本號、基準版本、修改者 ID 及時間戳記。
- **[REQ-FQC-09-04] 真實反饋與儲存中狀態**：後端確認寫入成功後，前端始得更新提示「草稿已儲存」及時間戳記；儲存過程中顯示「儲存中」；儲存失敗時保留當前所有輸入內容並彈出明確錯誤提示，不得假裝儲存成功。
- **[REQ-FQC-09-05] 重新登入自動復原**：使用者重新登入後，系統依權限查詢後端草稿，在畫面頂部清晰顯示未完成草稿提示，並提供「繼續編輯草稿」入口，無縫帶回完整編輯狀態。
- **[REQ-FQC-09-06] 讀取失敗防護**：若後端讀取失敗、登入 Session 過期或網路延遲，系統絕對不可將其視為「空資料」再寫回後端；嚴禁使用前端初始化之空值或舊快取覆蓋後端現有資料。
- **[REQ-FQC-09-07] 狀態指示**：介面上明確具備「未儲存」、「儲存中」、「已儲存」、「儲存失敗」四種狀態反饋；單純的「未儲存離開確認視窗」不能替代持久化保存機制。
- **[REQ-FQC-09-08] 併發與舊分頁防護**：多視窗、多分頁或多人員操作時，舊資料寫入必須經由後端 revision 樂觀鎖定檢查，舊版本嚴禁覆蓋新版本，衝突時明確提示並引導解決。
- **[REQ-FQC-09-09] 審核態持久性**：待審核（pending）、發回（rejected/revised）、已核准（approved）之狀態在使用者登出、關閉瀏覽器、重新整理與後端服務重新部署後，均完整保留。
- **[REQ-FQC-09-10] 歷史備份評估**：若後端有可恢復之歷史備份，由 Codex 保全並評估恢復，但絕不可覆蓋較新的線上有效資料；若確無備份可恢復，必須如實說明。

## 十、資料庫、員工同步與環境隔離 (REQ-FQC-10)

- **[REQ-FQC-10-01] D1 與 R2 分工**：沿用 Cloudflare D1（SQLite）保存結構化業務、關聯、草稿、版本、理由與審核資料；沿用 R2 Bucket 保存檢查方式圖片二進位內容，維持穩定之 Content-Addressed SHA-256 關聯。
- **[REQ-FQC-10-02] 三環境嚴格隔離**：
  - **Local (本機開發環境)**
  - **Staging (測試環境)**
  - **Production (正式環境)**
  - 各環境獨立具備本功能所需之結構、資料與圖片；本機與測試環境絕不連線或寫入 Production 資料庫。
- **[REQ-FQC-10-03] 唯一 Migration**：資料庫結構若需調整，新增單一唯一的 Migration 檔案，嚴禁修改已合併之歷史 migration。
- **[REQ-FQC-10-04] 冪等初始匯入**：初始資料匯入腳本具備可追蹤性、失敗可重試性與重複執行不重複建立資料（Idempotent）；後續程式更新與部署不得重灌覆蓋線上已有修改或進行中之草稿。
- **[REQ-FQC-10-05] GitHub 安全提交**：GitHub 僅保存程式碼、migration、經審核允許公開分享之 Canonical 標準資料快照、圖片清單與取得指令；嚴禁提交任何帳號密碼、金鑰、憑證或 Session。
- **[REQ-FQC-10-06] 沿用 `npm run data:sync`**：沿用或完善既有 `npm run data:sync` 機制；員工 Pull 程式碼後，執行指令即可將 FQC 標準資料及圖片同步至 Local D1/R2。
- **[REQ-FQC-10-07] 同步保護本機草稿**：執行資料同步時，必須保護並保留本機已存在之自定義草稿與未完成修改，若發生資料衝突需明確跳出警示供工程師選擇。
- **[REQ-FQC-10-08] 標準協同發布工作流**：建立「線上最新可分享資料匯出 → 更新 Canonical 資料版本與圖片清單 → 提交 PR 至 GitHub → 員工 Pull 後執行 data:sync」之協同流程，精確記錄來源、時間戳記、版本與校驗碼。
- **[REQ-FQC-10-09] 離線與 Git 邊界認知**：明確於文檔中說明 `git pull` 僅拉取程式碼，不會自動抓取雲端資料庫；線上修改必須透過上述標準程序更新 Canonical 快照。
- **[REQ-FQC-10-10] 禁止整庫盲目覆蓋**：嚴禁用 Staging 整個資料庫匯出覆蓋 Production，嚴防測試用帳號、虛擬案件或髒資料污染正式環境。
- **[REQ-FQC-10-11] 初始上線審核合規**：初次匯入資料應依循標準草稿與審核流程，清晰區分後台可見、待審與正式生效，嚴禁程式腳本繞過流程偽造核准標記。

## 十一、電腦版彈窗與捲動優化 (REQ-FQC-11)

- **[REQ-FQC-11-01] 視窗視口絕對居中定位**：彈窗（Modal）相對於當前瀏覽器可視區域（Viewport）進行居中定位，解決使用者目前「點擊後需向上大幅捲動才能看到視窗」的體驗問題。
- **[REQ-FQC-11-02] 任意捲動位置開啟可見**：無論頁面捲動至頂部、中部或最底部，點擊開啟彈窗時，彈窗標題與主要表單均立即呈現在使用者視線中央。
- **[REQ-FQC-11-03] 內容內部滾動與背景鎖定**：長表單內容僅在彈窗內部滾動，背景主頁面鎖定禁止滾動（`overflow: hidden`）；底部「儲存至草稿」與「取消」按鈕固定在彈窗底端，始終可見可點擊。
- **[REQ-FQC-11-04] 輸入與互動不跳動**：在彈窗中輸入文字、輸入理由/備註、勾選產品 Checkbox 或上傳圖片時，嚴禁重新構建整個表單 DOM 或重置滾動條位置。
- **[REQ-FQC-11-05] 關閉後位置與狀態保留**：關閉、儲存或取消彈窗時，背景頁面的滾動位置、搜尋關鍵字、線別類別篩選狀態及當前選定的錯誤代碼必須完整保留，不發生跳回頂部或重置。
- **[REQ-FQC-11-06] 取消放棄未確認內容**：點擊「取消」或右上角「返回」按鈕時，放棄所有臨時預勾選與未儲存輸入，不殘留至下次開啟。
- **[REQ-FQC-11-07] 專注電腦版驗收**：本次驗收聚焦桌面電腦版使用體驗，不額外加入手機端專用折疊改造。

## 十二、驗收與後續發布規範 (REQ-FQC-12)

Codex 實作完成後，必須逐項執行以下 **10 項必要驗收檢查**：

1. **[VERIFY-01] Excel 匯入與匯出驗證**：
   - 匯入指定 Excel（`FQC標準 FQC-C TRIL 1.xlsx`），確認 34 個類別、164 個錯誤代碼、508 個檢查項目完整解析。
   - 驗證異常回報視窗精確列出 3 筆半成品與 5 個空類別。
   - 重複匯入相同 Excel 驗證冪等性（不產生重複代碼或項目）。
   - 執行「匯出全部 Excel」，確認包含停用項目、無子項目的錯誤代碼、完整產品資料與圖片；匯出檔再匯入能 100% 還原。
2. **[VERIFY-02] 錯誤代碼與檢查項目維護驗證**：
   - 驗證錯誤代碼新增、修改、刪除功能；確認代碼與序號自動接續且唯讀。
   - 驗證包含子項目的錯誤代碼被阻擋刪除並給予提示。
   - 驗證檢查項目之新增、修改、停用、刪除及歷史紀錄保存。
3. **[VERIFY-03] 覆蓋矩陣互動驗證**：
   - 驗證矩陣正確呈現 `✓`（已啟用納入）、`—`（未納入）與停用標記。
   - 點擊 `✓` 直接取消關聯，點擊 `—` 直接加入；均不開彈窗、不變更其他項目內容。
   - 儲存後重開草稿與修改頁，產品勾選一致；儲存中重複點擊、失敗及修訂衝突均不得覆蓋新資料。
   - 驗證未涵蓋產品數量精確計算，且不受前端搜尋/篩選干擾。
4. **[VERIFY-04] 變更理由機制驗證（2026-09-22 規則）**：
   - 驗證錯誤代碼新增或名稱實質變更時理由為必填；未變更名稱時不要求填寫理由。
   - 驗證錯誤代碼同一草稿中已填寫之理由重新開啟自動帶回。
   - 驗證檢查項目表單與覆蓋矩陣全面無變更理由欄位，操作與儲存不阻擋或要求填寫理由。
5. **[VERIFY-05] 草稿持久化與跨 Session 驗證**：
   - 建立草稿並修改文字、勾選產品、上傳圖片、填寫理由後點擊「儲存草稿」。
   - 依序測試：重新整理網頁（F5）、關閉瀏覽器後重新開啟、主動登出後重新登入。
   - 驗證重新登入後系統能找到原草稿，顯示未完成提示，並可繼續同一份草稿之編輯。
6. **[VERIFY-06] 完整審核閉環驗證**：
   - 編輯草稿 → 儲存草稿 → 送出主管審核（版本切換為 pending 且鎖定）。
   - 以主管身分登入「版本確認平台」→「品質系統資料庫」分頁，確認待確認筆數與案件存在。
   - 點擊查看差異比對，確認新增/修改/刪除/產品/圖片/理由完全符合。
   - 執行「發回並填寫理由」→ 編輯人員重新登入看見發回提示與理由，解鎖草稿繼續修改 → 再次送審。
   - 主管執行「確認版本（核准）」→ 生效版本切換，舊版轉為 superseded。
7. **[VERIFY-07] 併發與失敗防護驗證**：
   - 模擬網路中斷或後端報錯，驗證系統不假報儲存成功，保留前端輸入內容。
   - 模擬多分頁同時編輯舊版資料，驗證後端樂觀鎖定阻擋舊資料覆蓋新資料。
8. **[VERIFY-08] 員工資料同步驗證**：
   - 建立乾淨環境，執行 `npm run data:sync`，驗證本機 D1 與 R2 能完整取得 FQC 標準資料與圖片。
   - 在本機有自定義草稿時再次執行同步，驗證本機草稿未被清除。
9. **[VERIFY-09] 桌面彈窗與捲動驗證**：
   - 將瀏覽器滾動至頁面頂部、中央、底部，分別點擊修改代碼、修改檢查項目。
   - 驗證彈窗均在視窗正中央開啟；輸入文字、填寫理由、點擊勾選時頁面完全不跳動；關閉彈窗後背景位置保持不變。
10. **[VERIFY-10] 重新部署持久性驗證**：
    - 模擬重新執行部署，驗證正式資料庫中的生效版本、待審案件、草稿及 R2 圖片未遺失。

## 十三、Codex 發布與最終結案要求

Codex 實作完成後，發布流程必須嚴格遵守專案規定：
1. 依專案規範提交工作分支，發起 Pull Request。
2. 通過本機所有現有 checks（包含 `oxlint`、`oxfmt`、相關測試腳本）。
3. 經 Frank 審查並完成 PR 合併至 `main`。
4. 部署至 Staging 測試環境完成全流程驗證。
5. 進行 Production 正式資料庫完整備份與還原測試。
6. 取得 Frank 針對該 SHA 的 Production 授權後，執行 Migration、資料匯入與正式部署。
7. **最終結案報告需包含**：
   - 完成/未完成項目清單
   - 草稿遺失之確切根因與修復證明
   - Excel 匯入數量與異常處理結果
   - 各環境（Local / Staging / Production）資料與圖片驗收結果
   - 實測通過之驗證項目與無法實測之項目說明
   - 員工同步指令（`npm run data:sync`）
   - 合併之 Git commit SHA 與線上發布網址
   - **嚴禁將 UI 完成或程式碼合併誤報為資料庫與部署完成**。
