# FQC single-plan reconciliation

Only arm after the owner has independently identified the original FQC operation using the existing original-page reference and verified the full selection is one source/product/period. The historical operation and its receipt are preserved. Empty lists and a missing receipt establish neither authorship nor non-write.

For an existing plan, verify the linked document, exact scope, dates and owner receipt. If the original dates are unknown, use independently verified document dates for preservation. For an unassigned current job, first select the new plan dates with the owner. The confirmation displays the proposed product, source, period and plan dates. These are dates for a new authorized plan. Do not describe them as recovered historical inputs. On mismatch stop and recheck without writing.

Require the original Site, its canonical HTTPS origin, verified GitHub application merge (build and runtime PROCESS_PROGRAM_COMMIT), mapped projected source version and native DB binding. Independently verify the target and completed transfer. Apply only the additive 0010 migration after checking the target's existing migration journal. The separate one-use ledger survives application snapshot restoration; a complete database restore requires a separate investigation. Do not repurpose existing business receipts or import tables.

Only after separate action-time authorization use a private FQC_PLAN_ONE_TIME runtime secret with the fields defined in lib/routine-plan-maintenance.ts. Generate a distinct registered FQC plan intent identifier. Allow at most one hour. Deploy the approved saved version to apply the configuration. Use the original FQC page's read-only receipt lookup, confirm the displayed selection once, and verify independent readback. A missing/mismatched proof leaves the original pending. Remove the grant and apply the environment revision through an authorized deployment. Keep the ledger, audit and backups.
