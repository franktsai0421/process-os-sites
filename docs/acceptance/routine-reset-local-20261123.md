## Implemented behavior

- FQC and IQC keep separate buttons, exact scope confirmations and independent JSON control owners. No all/both action. Other-module data, audit, pending and browser epoch remain unchanged.
- Reset atomically saves a monotonic module `resetGenerationRevision` with the cleared control. Ordinary FQC/IQC executors check the original expected revision before replay or mutation, on every CAS retry. New FQC commands after reset include this module revision; an uncertain original request is never upgraded or resent. Whole-page FQC retains its random draft generation fence.
- `resetLedger` retains scoped Reset IDs, actor, time, reason, revision, matched pending evidence and minimal operation tombstones. Ordinary committed receipts retain actor and fingerprint hash, not document payload. Registered intents are distinguished from committed operations. Missing original receipts remain `unknown`, explicitly `superseded-by-reset`, never failed or successful by inference. Legacy first-start retirement evidence is retained. Repeat Reset preserves earlier audit and lookup/replay receipts.
- The ledger rejects malformed state, mixed scopes, reappeared retired receipts and exhausted capacity (256 reset entries / 10,000 retired operation IDs / 1,000,000 serialized characters). Protective evidence is never pruned to make Reset succeed.
- New writes cannot reuse retired IDs, even with a current revision. Plan-intent POST and whole-page POST check the same tombstones. Existing first-start retirement refuses reset controls. Ordinary stale requests retain the request's original revision across retries.
- Each ordinary UI supplies only its actor's exact pending IDs and a digest of the exact storage key/value. After owner-authorized Reset, receipt lookup and fresh generation readback precede removal of matched markers. Changed evidence stays blocked; other markers stay intact. A lost Reset reply is recovered with GET only. Double-submit tests assert one POST.
- Scope-specific browser epochs invalidate old ordinary responses and callbacks, including the separate FQC photo callback. FQC invalidation does not invalidate IQC's active client, or vice versa. Account authEpoch and global delivery state are not changed. Updated cache tags load the new scripts.
- Protective ledger contents are omitted from ordinary FQC projections; only the selected owner's Reset proof is returned through the existing authorized reset route.

Logical generated rows, plans, reports/cases and review histories are cleared from the selected control. Source definitions/frequencies, other modules, site settings, existing R2 photos/immutable storage and backups are retained. This is not a physical archive/media purge. An already-started R2 upload can leave an unreferenced object; this change prevents stale attachment to business state, not an atomic cross-D1/R2 deletion.

## Rebuilt authority and enrollment

Public entry remains unchanged. Reset is OFF unless a native-provisioned `PROCESS_ROUTINE_RESET_ACTIVATION` passes exact project/origin, compiled hosting identity, release commit, expiry, application owner and DB target/transfer/bootstrap lineage checks. Required native `oai-authenticated-user-id` must match a server-held hash or confirmed enrollment. Email, Host, username and the former second DB alias grant nothing. The independent existing primary platform owner session and permissions remain required. POST requires same-origin JSON and rejects cross-site requests. Final reset CAS includes the DB-lineage predicate and rechecks activation.

`PROCESS_ROUTINE_RESET_ENROLLMENT` is a separate default-OFF grant with the common pins, a unique opaque enrollment ID and a fresh secret. Only the existing authenticated app owner can open `/api/routine-reset-enrollment`. Normal top-level Sites sign-in uses the supported `/signin-with-chatgpt?return_to=...` route; no custom OAuth or bypass. Owner explicitly confirms the current native Sites account is their own. GET does not enroll; two explicit button actions prepare and confirm a five-minute, session/native-identity/grant-bound one-use proof. It writes only protected metadata, not business data, and never enables Reset. Current runtime trust requires native Sites dispatch as the only ingress; simulated headers in tests do not establish safety on an arbitrary direct Worker endpoint.

`routineResetEnrollments` uses existing shared JSON storage, bounded to 32 entries. Only hashes of native identity, session, token and grant are stored with owner/context and timestamps. No raw identity, secret, cookie or token is logged or returned in status. Public state omits the key and generic writers reject it. The browser keeps its opaque token only in memory and clears it on error/pagehide. Lost confirm replies use read-only lookup. Lost begin reply cannot recover the token: expire it and provision a new unique grant; no pruning/reissue. Confirmed enrollment persists, while activation has its own expiry. Neither enrollment nor capability lookup clears records.
