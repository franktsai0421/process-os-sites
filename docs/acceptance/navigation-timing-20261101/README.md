## User interface and control

After approved deployment, the existing administrator opens `/navigation-timing`. Its read-only `/api/navigation-diagnostics` gate uses fresh existing identity checks, rejects anonymous/demo/non-admin sessions and returns only enabled/expiry metadata. Start, Refresh and Export each recheck that same fresh gate and fail closed on denied, unavailable, off or expired results. Failure stops the recorder and hides the current summary; previously downloaded files cannot be recalled. The page has bilingual start, refresh, stop, export and clear controls plus links to login, dashboard, editor, process master and FQC. It does not navigate or log in automatically. Current app page access and all existing business permissions still apply.

Server-side enablement requires both nonsecret settings:

- `PROCESS_NAVIGATION_TIMING=1`
- `PROCESS_NAVIGATION_TIMING_UNTIL=<explicit UTC ISO expiry>` strictly in the future and at most 24 hours away.

These settings have not been changed on any Site. The parent should choose a short expiry for the authorized observation window. Missing, disabled, expired or excessively distant settings deny sampling. Setting the flag to `0` (or removing it) is the server kill switch; expiry is automatic. Stop and Clear remain enabled during a pending diagnostic authorization request. They invalidate the private action sequence and abort only that config GET; late success/failure cannot restart collection, export, restore a summary or disturb a newer action. Unmount also invalidates pending actions. Stop is the same-tab browser kill switch and retains summaries. Clear also empties recorder RAM and storage; subsequent snapshots and queued save callbacks cannot restore cleared rows. Restoring the source change is a separate normal reviewed release, not a special deployment mechanism.

The UI arms only its own sessionStorage tab for at most ten minutes and no later than the server expiry. It retains at most 240 sanitized event rows, samples at most 60 eligible requests per document and stops its fetch/observer hooks on expiry. Old local rows are discarded when the diagnostic page is reopened more than 20 minutes after the collection expiry; tab closure or clear also discards the session storage (browser session restoration behavior is browser-owned). Downloaded exports are user-owned files, not centrally retained reports. The server admits at most 30 successfully authorized non-demo-admin samples per minute **per isolate**, not a global/account quota. It keeps at most 64 detailed intervals plus fixed-name cumulative counters per request. Dropped detailed intervals are reported. Streaming instrumentation stops after a 120-second request lifetime; missing terminal data stays unknown.

The recorder is embedded in compiled HTML, not fetched as an extra blocking script. Default-off normal pages perform a single sessionStorage lookup and return before installing observers, fetch wrappers or event listeners; the inactive diagnostic page only reads retained rows and also installs no hooks, observer or timer. Teardown is idempotent and restores only its own fetch wrapper; HTML still contains the recorder bytes. The raw, uncompiled process HTML has a build marker only; this feature targets the compiled Site build. Ordinary response bodies, request bodies and business call order remain unchanged. No client polling, background preload, extra per-request auth read or third-party telemetry is added.

## Exact data boundary

Only fixed route/type labels, GET/POST, status, numeric timestamps/durations/counts/bytes, fixed outcomes and random non-identity document/request IDs are exported. IDs are correlation values, not credentials or retrieval capabilities. Absolute browser time-origin timestamps allow login-to-document correlation. No account, role, product, DOM text, URL/query/hash, cookie, arbitrary header, SQL text/parameters, object key, request/response body, exception text or screenshot is recorded by the diagnostics.

Request headers are preserved to add the fixed opt-in `X-Process-Timing: 1`; they are not logged or exported. `Server-Timing` is parsed into the strict numeric/fixed-label schema and never exported as arbitrary header text. Full response transfers join their request/response rows by the same random server request ID when the browser exposes same-origin Server-Timing. Uninstrumented same-origin resources use the generic `other` label. Cross-origin resources are not collected. Event-row count is capped, so exports are a bounded window, not an unbounded total request ledger.

The backend emits timing only for a successful 200 response whose existing identity checks verified a current non-demo admin on six audited routes: normal platform login, process bootstrap, process-authoring workflow GET, master workflow GET, FQC workflow GET and equipment workflow GET. Credential login passes its verified account role/type after password/session work. Ordinary identity checks pass their existing verified result into request-local diagnostic admission without any extra auth/DB read; a failed or restricted check permanently suppresses that request. Bounded pre-auth spans remain unpublished memory until admission. The header is only an untrusted opt-in, never proof of privilege. Quota is consumed only after successful authorization and response checks. Logout, demo login, business POST, errors, revoked/forbidden/anonymous requests and unsupported routes emit no timing header or metric log. The recorder stops when a supported sampled response lacks authorized timing (including quota exhaustion), without altering that business response. Revocation is observed at existing request checks and at UI action revalidation, not through background polling or push. In-flight work authorized before a later revocation is not retroactively cancelled. Per-token revocation follows the existing deployment flag; no flag/ACL is changed here. Recording does not grant access or avoid current revocation, revision, CAS, receipt or readback checks.

Ordinary JSON responses return measurements in `Server-Timing` and do not duplicate them into logs. For streamed workflow responses, a bounded `process-navigation-timing-v1` record in the **existing Worker log sink** supplies completion/cancel/error intervals after response headers. It contains only the above safe metrics. Existing provider request metadata, availability, sampling and retention are platform-owned and were not modified or verified by this worker. There is no new DB/R2 metric store. Parent log access must select the random ID and export only the diagnostic payload, not surrounding request metadata.

## What each measurement means

| Evidence | Meaning and limit |
| --- | --- |
| Browser click / submit | Explicit known navigation or login form intent; never form values |
| Browser document/resource timing | Navigation/fetch start, DNS, connect/TLS, request start, response start/end and browser byte counters; 0 transfer bytes is not automatically proof of a cache hit |
| Browser request / response | Fetch invocation to response headers, with exact same response object; no cloned/body read |
| ready / paint | Existing authoritative generation/status/boot readiness and two following animation frames; login uses its mounted client effect. Physical-device responsiveness, image completion and input latency are separate |
| shared/assets/ready fields | Existing performance-origin endpoints, not exclusive additive phases |
| `pt` / serverMs | Application handler entry to response construction; excludes platform dispatch before the handler, browser transport and streamed tail |
| `auth` | Actual identity/password/session operations wrapped in this request; not a claim to measure every authorization predicate separately |
| `db.first/all/run/batch` | Await of the original D1 call, native receivers/statements preserved; batch count means calls, not SQL-row counts |
| `r2.get/head/put/text/arrayBuffer` | Original binding/body operations, no reread; get bytes are logical object size, arrayBuffer bytes are decoded body length, other unknown byte fields are -1 |
| `decode` | Existing record/chunk hydration scope including child I/O; specific instrumented JSON.parse calls also have separate `parse` spans |
| `projection` / `serialize` | Wrapped current projection/adapter work and actual Response.json / streaming fragment serialization; not an exhaustive profiler of every helper |
| interval parent / start / end | Nested and parallel spans. Never add their durations to derive request wall time |
| fixed-name totals | Count and cumulative operation work duration, including intervals beyond the 64-row detail cap; parallel work totals are not wall time |
| stream terminal log | Tail can include consumer backpressure. Correlate by request ID; it is not pure CPU or DB latency |

Worker clocks can have coarse/IO-dependent resolution: a synchronous parse/serialize value of 0 does **not** establish zero CPU cost. Worker CPU is not synthesized from wall-time subtraction. Missing headers, cap/expiry, missing logs, incomplete streams, arbitrary JS work, unwrapped helper internals and platform/network gaps remain unknown. The UI shows a dash when no server measurement is supplied. DNS/TLS/connection fields can overlap; do not sum them with request/app spans. The application interval is contained in a wider request, so subtracting it from browser TTFB does not uniquely identify network, TLS, queueing or platform dispatch.

Parent-provided existing v33 evidence (not collected here): five anonymous `/login` HTML requests at 17:52:47–17:53:59 UTC had assistant HTTP totals 5960/2731/3224/3005/2694 ms and matched Worker wall 51/17/14/9/10 ms, CPU 47/16/14/8/9 ms. This supports a large gap outside the reported application Worker span, not a DB/R2 bottleneck or employee-network conclusion. `/process/` HTML lacked matched Worker records; that is not proof no request occurred. Those were not login POST, rendering or FQC data measurements. This diagnostic keeps those boundaries separate.
