# FQC Reset read diagnostic

The original test Site's Reset failed during the full shared-state read. The application helper reads a D1 row and hydrates records from R2. Native Worker logs can correlate an application message to the request, but the existing event does not identify the failing storage operation.

For an independently reviewed publication, an operator can set `PROCESS_FQC_RESET_READ_PROBE_FROM` to an ISO UTC start timestamp with milliseconds. The window lasts ten minutes and must fit inside the existing Admin FQC Reset activation. The separate switch defaults off. A signed-in application Admin with the normal FQC Reset permissions pastes `/api/routine-reset?scope=fqc&diagnostic=read-state` after the original Site origin in the browser address bar and visits once. The browser must send a user-activated top-level navigation with `Sec-Fetch-Site: none`. No page code invokes this selector. Use a browser that supplies these headers. Do not synthesize them or clear pending receipts.

The operator response contains only fixed `stage` and `category` strings. The same pair appears in the `routine_reset_read_probe` information event in native Worker logs when an authorized probe reaches its result. Use the all-level read-only log view. Access or recheck failure returns a generic denial. The selector does not call the Reset writer. Authority and the selected authorization state must be readable first. The response requires a final session, permissions, revision, activation and time-window check.

The probe runs the same D1 SELECT and records-v1 decoder as Reset, with limits of 128 R2 lookups, 8 MiB cumulative fetched size, 8 MiB expanded immutable bodies, and 1 Mi UTF-16 units for the manifest. The diagnostic caps nesting at 64, each container at 2,048 members, and cumulative structural units at 65,536 across fetched values, manifests and repeated body expansions. A 15-second deadline is checked between I/O operations and cannot interrupt a provider call already in flight. Each Worker isolate admits one full read per window. There is no global deduplication or persistent rate-limit write. A budget result or unsupported format leaves the underlying storage failure undetermined. A healthy result describes this read only. No business values, keys, identifiers, provider messages or stacks are returned or logged by the probe.

Synthetic checks cover D1, provider lookup, absent object, body read, hash mismatch, malformed nested JSON, cached-body expansion, permissions, drift and prefetch rejection. Tests compare full-read D1/R2 order with the production reader and check unchanged SQLite state, unchanged object bytes and zero storage-write events.
