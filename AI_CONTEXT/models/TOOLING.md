# Tooling implementation and model

2026-10-28 cloud candidate; not deployed and no native browser acceptance.  Requirements: [TOOLING](../../docs/specs/current/TOOLING.md); environment-specific results: [initial import](../../docs/tooling/20261006-acceptance.md), [UI acceptance](../../docs/tooling/20261007-ui-acceptance.md).

- `toolingMasterControl`: schemaVersion 1, activeVersionId, numeric versions, V3 workflow (`scope=tooling`), reservedCodes per collection, pinned importSource, transferApprovals keyed by transfer ID. Uses existing D1 shared_state CAS and records-v1 R2 immutable bodies; no new table or migration.
- Snapshot arrays: tools, categories, custodians, suppliers, manufacturers, transfers. Tool IDs and catalog IDs are stable; initial source IDs include original codes. Codes are server allocated and reserved outside historical snapshots, so deletion or restore cannot reuse a number.
- Tools contain separate nameVi/nameZh, categoryId, assetCode (not unique), specification, positive whole-group quantity, original unit, manufacturerId, initial location `{kind,holderId}`, inboundDate/inboundDateLost, enabled/inactiveReason, archived/archiveReason, notes, frequencyMonths, photos, iqcIds, original iqcSource and readonly Excel source provenance.
- Catalog contact fields are independent arrays. Custodians have only names/ID and no business code or enabled state.
- Optional `inspectionFrequency` is `weekly|monthly|quarterly|semiannual|annual|null`; new selections require matching `frequencyMonths` (`null|1|3|6|12`). Weekly is explicit and never inferred from a fractional month. Legacy snapshots without the field retain their positive month values; unrelated edits do not rewrite them. This adds an optional JSON field only, with no SQL migration or workbook conversion.
- Photos are SHA-256 IDs in `tooling/photos/{id}` served by `/api/tooling/photo`; no base64 in snapshots. Source anchor/index metadata remains with each imported photo. PUT checks live roles, origin, MIME and bounded 25 MB stream; GET checks live data/review permissions.
- IQC references use approved stable part IDs. `lib/tooling-iqc.ts` projects active/disabled/removed status and sourceVersionId from approved/superseded snapshots only, retaining tombstones and removed historical identities. New choices require enabled/nondeleted formal parts; unchanged exceptional references remain nonblocking reminders. `/api/tooling/iqc?partId=` returns a readonly formal/historical source snapshot rendered with IQCMasterUI's existing detail component; it does not load or change IQC working drafts. IQC's optional `isEnabled` defaults to enabled for older parts; existing code immutability and unique code rules remain.
- Transfers have stable ID, toolId, from/to, reason, optional correctionOf, server-created/updated actor/time, and optional captured quantity/unit for new records. Legacy records are not backfilled with invented historical quantities. Active snapshot transfers are immutable. Correction chains replace the target movement at its original position in the ordered movement sequence. Only a destination with a known holder changes effective location; incomplete destinations retain the previous known position. New movement sources are server guarded against preceding effective movements. Draft transfers do not mutate active location or quantities. Approval metadata remains outside immutable case contents.
- `lib/tooling-workflow.ts` adapts `versionedWorkflowRoute` and `shared-draft` with field patches and dependency guards, monotonic allocation, reference/deletion checks, exact source provenance and first-import conflict guard. New unclassified tools receive reserved DC00 numbers without guessing a category. Business findings (including missing translation and destination) are nonblocking, with fixed case reminders. The adapter retains the user's tooling no-change submission guard; ADMIN self-review uses the existing explicit confirmation and records the actor/time. Module read permission grants tooling history/source/media access; approval remains separate. No shared kernel policy changes in this repair.
- A new prepared model registers its state key before record encoding; this fixes an otherwise successful begin response whose brand-new module was absent after reload. Existing keys retain their prepared-body encoding behavior.
- Public shared-state projection strips working/saved/cases and only exposes the active version. `/api/tooling/checks` uses the same authorized workflow reader; results identify generation/revision and separate working/saved findings.
- Whole-state restore interlock evidence belongs to the historical 2026-10-06 fixture. This Sites derivative has no `app/api/backups/route.ts`; the older `test-tooling.cjs` is not a complete current acceptance run.
- `public/process/tooling.js` mounts VersionDraftUI and uses shared-draft-client with guarded dialog confirmation. Whole-scope Submit uses the last successful manual Save; it never implicitly saves. Existing CAS/receipt/unknown-result handling remains. Catalog CRUD is inline below filters with distinct readonly View, Edit and Delete. Photos/location live in Basic; IQC cards show approved source state/images/details. New transfer source is readonly; correction preloads the chosen approved record. Collapsed history includes actor/time and approval version. Review numbers come from the existing bounded uiHistory metadata reader. Only foreground mutation/read admission owns action busy state; four-second background reads do not flicker Begin. Read epochs discard responses superseded by user actions/navigation. Advisory checks load after primary readiness, deduplicate same-source requests, carry state/active/saved/IQC source metadata and reject mixed revisions; loading/failed never means zero issues. Visible idle pages poll at four seconds without replacing editor inputs; immutable before/after history delegates to openSharedDraftHistory.
- `/api/tooling/local-handoff` is Local-only and normal ADMIN-only. GET exports complete archived versions, saves, receipts, sequences and cases. POST checks approved closed source, digest, target revision and media, stores an exact backup without pruning, then writes only toolingMasterControl using CAS. Existing different targets require explicit `expectedTargetDigest`, a closed target and retained complete history: former active approved version may only become superseded; old cases/saves/receipts/tombstones/transfer approvals remain, codes stay reserved and sequences never decrease. Divergence fails closed. Exact replay is idempotent. No remote access, Git operation or SQL migration. Evidence: [flow acceptance](../../docs/tooling/20261007-flow-acceptance.md), [V12 retirement](../../docs/tooling/20261007-retirement.md).
- Import tooling: `scripts/tooling-import-dry-run.py` validates package manifest and readonly XLSX, emits deterministic payload/original media/provenance/mapping; `scripts/tooling-import-local.mjs` only targets isolated 3030, refuses existing differences, verifies backup before writes, uploads original hashes, applies then saves without submit. `scripts/verify-tooling-local.mjs` checks exact saved/working payload, all original images, approved IQC references, only tooling state changed, no public draft leak, and the original 3000 database digest.

The current import deliberately holds five source-image identity issues. No old inspection or transfer approval events are imported. Full source/backup/evidence paths and counts belong to the acceptance report, not runtime constants.

The 20261006 port 3030 runtime is retired. Its metadata blocks both old import and initial verification scripts before network access. Archived D1/R2 remain for recovery; future 3030 work requires a fresh directory and baseline.
